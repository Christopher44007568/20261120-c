# 可见性缓冲与延迟渲染基准

## 实现与口径

- 第一遍真实软件光栅化，只写可见三角形 ID 与深度；不写法线、反照率、材质参数。
- 第二遍按 ID 分块读取三角形属性、解算材质并着色；G-buffer 路径使用完全相同的着色函数。
- 两条路径的 8 位输出 checksum 必须一致，否则基准直接失败。
- 带宽为等效渲染目标流量模型：包含深度测试读、深度写、G-buffer/可见性缓冲读写、三角形属性读取和最终颜色写。不包含两边共有的顶点索引、三角形剔除和命令开销。
- 可见性记录为 `triangleId(4B) + depth(4B) = 8B/px`；G-buffer 为 `32B/px + depth(4B) = 36B/px`。
- 三角形属性读取按 16x16 解算 tile 去重，记录大小 100B；这是对 tile 内属性缓存局部性的建模。
- 时间取 3 次运行的中位数；CPU 软件光栅化时间只用于相对趋势，不是 GPU 硬件计时。

## 多材质比较

| 场景 | 材质数 | 可见性带宽 | 延迟带宽 | 可见性着色耗时 | 延迟着色耗时 |
|---|---:|---:|---:|---:|---:|
| dense_small_8mat | 8 | 84.81 MiB | 246.09 MiB | 44.74 ms | 30.63 ms |
| dense_small_64mat | 64 | 84.81 MiB | 246.09 MiB | 44.83 ms | 29.40 ms |

两组多材质场景的几何和屏幕覆盖完全相同：材质数从 8 增至 64 时，两种管线的带宽基本不变。延迟渲染把 material ID 和统一格式属性写入每像素 G-buffer；可见性缓冲从三角形记录获得材质，因此材质数量不受 G-buffer 布局约束，也便于按材质间接派发。代价是第二遍存在三角形属性随机读取，需要 tile 聚类和缓存。本基准中增加材质数没有增加带宽，着色耗时也保持在噪声范围内。

## 结论

- **大量小三角形场景**：`small_triangles_8mat` 的可见性缓冲带宽为 32.08 MiB，延迟渲染为 70.31 MiB，降低 54.4%。
- **高三角形密度**：`dense_small_8mat` 的 691200 个三角形、6 层覆盖下，可见性缓冲降低 65.5%。
- **高密度小三角形真实压力**：`tiny_dense_64mat` 的 1843200 个约 2 像素三角形、4 层覆盖下，可见性缓冲仍降低 45.0%，确认优势在该压力场景成立。
- 可见性缓冲的主要收益来自减少高密度几何的每片元写放大：每个通过深度测试的片元只写 4B ID（加 4B 深度），而不是延迟管线的 32B G-buffer。
- 这组测量中可见性缓冲的第二遍解算+着色为 44.7–50.6 ms，延迟为 29.3–30.6 ms。可见性缓冲省的是带宽，不是无条件省算力；真实 GPU 上还需用 tile 属性缓存、压缩顶点和材质间接派发隐藏随机读取成本。
- 限制：若单个可见三角形只覆盖极少像素，100B 属性读取按像素摊销后会接近甚至超过 G-buffer 读取；因此真实实现应使用 tile 内 ID 去重、属性缓存和压缩顶点格式。
